# DAG-Factory Pattern for Large Estates

An AutoSys estate carries job/box definitions as data (JIL), not code. The Astro-side design that preserves this property — rather than hand-writing one Python DAG file per box — is a **DAG factory**: workflow definitions kept as data (YAML/JSON, one file per box), plus a small number of Python modules that read that data at parse time and generate DAG objects [F1][F2].

## Core mechanics

- DAGs can be generated inside a loop using the `@dag` decorator or `with DAG(...)` context manager; Airflow registers every DAG object produced this way automatically [F1].
- {syn: F1,P1} Map each AutoSys box definition to one factory config record — this preserves the existing per-box JIL granularity (`reference/mapping.md`'s box→DAG boundary decision tree already governs *whether* a box becomes its own DAG or a TaskGroup; the factory pattern governs *how* whichever shape wins gets generated at scale, not a replacement for that decision).
- Tasks and TaskGroups generated by the factory **must be produced in a stable, deterministic order on every parse** (e.g. `sorted()` over the config keys) — non-deterministic ordering across parses causes spurious DAG-structure changes [F3].
- Complex per-box metadata should be exported to a file in the DAG folder (JSON/YAML) rather than computed or fetched by top-level code at parse time — top-level code runs on every scheduler parse cycle, not just at trigger time [F4].

## Estate-scale decision table

| Estate size | Recommendation |
|---|---|
| Hundreds of jobs (dozens of boxes) | A single factory module reading one directory of YAML configs is sufficient; no sharding needed. |
| Thousands of jobs | {syn: F5,F6} Split factory configs by business domain/team into separate subdirectories, each parsed by its own factory invocation — this keeps `min_file_process_interval`'s per-file parse cost bounded per domain rather than one monolithic parse growing with total estate size [F5]. Also size `parsing_processes` to roughly 2x available scheduler vCPUs [F6a]. |
| Tens of thousands of jobs | {syn: F4,F5} Beyond domain-sharding, avoid any I/O or computation in the factory's top-level code path (no API calls, no DB queries at parse time) [F4] — at this scale, even cheap per-file operations are multiplied by `min_file_process_interval`'s parse cadence (default 30s) across every shard file [F5]. If factory generation itself becomes measurably slow, increasing `min_file_process_interval` trades DAG-change responsiveness for scheduler load — a real tradeoff to make explicitly, not a default to leave untouched at this scale [F5]. |

## Migration-temporal callout

{syn: F7} During AutoSys/Airflow coexistence, the factory can pass `is_paused_upon_creation=True` to the DAG constructor for boxes not yet cut over, so newly-generated "shadow" DAGs don't start executing before their AutoSys counterpart is turned off — this is a factory-config concern (one extra field driving a real DAG constructor argument), not a separate code path.

## What this does not replace

The factory pattern is purely a *generation mechanism*. It does not decide box→DAG vs. box→TaskGroup (`reference/mapping.md`), condition-string translation (`reference/conditions-and-dependencies.md`), or calendar/Timetable design (`reference/calendars-and-scheduling.md`) — those decisions are made once per box and stored as factory config fields, not re-derived by the factory itself.
