# Metadata DB Growth at Scale (Thousands of DAGs)

At the scale of thousands of DAGs, Airflow's metadata database (PostgreSQL) is placed under extreme load. Without proactive tuning, this manifests as slow task scheduling, sluggish DAG parsing, and UI timeouts [B1][B2].

## 1. Database maintenance (The most critical factor)

Airflow does **not** automatically delete historical data. Tables like `task_instance`, `dag_run`, `log`, and `xcom` will grow infinitely [B3].

*   **Action**: Implement an automated "Cleanup DAG" using the `airflow db clean` CLI command to purge records older than a specific retention period (e.g., 30–90 days) [B3][B4]. **Correction (cross-file consistency)**: on **Astro Hosted**, this isn't a plain CLI call from a DAG task — tasks in Airflow 3 cannot access the metadata DB directly, so `airflow db clean` must be wrapped in an Airflow plugin that exposes it; running it as written here would silently fail on Hosted. See `reference/metadata-db-and-state/metadata-retention-and-cleanup-policy.md` in this skill for the correct per-deployment-model mechanism (Astro Hosted vs. self-managed Astronomer Software). (See topic 027 for detailed retention policies).
*   **Database grooming**: Regularly run `VACUUM ANALYZE` on PostgreSQL to reclaim space and update query planner statistics [B2].

## 2. DAG authoring optimizations for DB load

At scale, poor DAG authoring directly degrades database performance:

*   **No Top-Level Code**: Never execute database lookups (e.g., `Variable.get()`, `Connection.get()`) at the top level of a DAG file. These execute every time the scheduler parses the file (e.g., every 30 seconds), creating massive unnecessary DB load [B5][B6].
*   **Use Jinja Templating**: Access Variables and Connections via Jinja (`{{ var.value.my_var }}`) so the DB lookup only occurs at task execution time, not during parsing [B6].
*   **Limit XCom Size**: Passing large datasets via XCom bloats the metadata DB rapidly. Use a custom XCom backend (S3/GCS) for large payloads (see topic 032) [B7].

## 3. Infrastructure tuning

| Component | Tuning action |
|---|---|
| **Database Connection Pooling** | Essential. Use PgBouncer to manage the high volume of concurrent connections generated by thousands of DAGs and tasks [B2][B8]. |
| **Scheduler Scaling** | Run multiple Airflow schedulers (Active-Active) to distribute parsing and scheduling load [B9]. |
| **Database Hardware** | Ensure the PostgreSQL instance is provisioned with high IOPS and memory. Monitor `EXPLAIN ANALYZE` for slow queries and consider custom indexes on `task_instance` if needed [B2][B10]. |
